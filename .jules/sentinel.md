## 2026-08-14 - Temporary Path Traversal & Substring File Deletion in Room Image Uploads
**Vulnerability:** The `RoomController`'s store process processed user-supplied temporary paths (`temp_cover_path` and `temp_gallery_paths`) without prefix or traversal validation, exposing copy/deletion of system files like `.env`. Furthermore, the `deleteTempImage($tempId)` endpoint used a loose `str_contains` check, allowing authenticated attackers to delete arbitrary files via substring match.
**Learning:** Storing and retrieving user-supplied temporary file paths without strict directory constraints and filename pattern matches creates critical directory traversal and arbitrary file manipulation vectors.
**Prevention:** Validate all temporary uploaded paths to ensure they strictly reside within designated directories (e.g. `temp/room-images/`), contain no traversal segments (`..` or `\`), and match a strict filename format. Always delete temporary files using exact filename matching (`pathinfo(..., PATHINFO_FILENAME) === $tempId`) instead of loose substring searches.

## 2026-08-05 - Missing Global HTTP Security Headers (Defense in Depth)
**Vulnerability:** The application was missing standard HTTP security headers (such as `X-Frame-Options`, `X-Content-Type-Options`, `X-XSS-Protection`, `Referrer-Policy`, and `Content-Security-Policy`), leaving web responses vulnerable to clickjacking, MIME-type sniffing, and cross-site data leakage.
**Learning:** Default framework configurations often omit strict security headers, leaving clickjacking and data leakage vectors unmitigated out-of-the-box. A central global middleware is the cleanest mechanism to consistently apply secure default transport headers across all web routes.
**Prevention:** Register a global or group-based HTTP middleware that appends essential security headers (including HSTS when in production) to all outgoing HTTP responses, and enforce presence with dedicated integration tests.

## 2026-07-27 - Null Key Webhook Signature Bypass
**Vulnerability:** Webhook signature verification in `BookingController::verifyPaystackSignature` referenced `config('paystack.secret')` which does not exist in the configuration file (`config/paystack.php`). Since the key was missing, it resolved to `null`, allowing an attacker to bypass signature verification entirely by computing signatures against an empty key.
**Learning:** Referencing non-existent configuration namespaces can result in silent failures where security-critical keys resolve to null or fallback defaults. Furthermore, standard PHP loose comparisons (like `===`) don't prevent timing attacks, and lack of strict null/empty checks can expose cryptographic bypass vectors.
**Prevention:** Always verify that configuration keys referenced in code exactly match those defined in config files. Implement robust pre-validation checks to ensure security-critical parameters (such as secrets or incoming signature headers) are neither null nor empty before performing cryptographic checks. Utilize `hash_equals` instead of `===` for cryptographic string comparisons to defend against timing-based side-channel attacks.

## 2026-07-29 - Storage Route Hijacking & Path Traversal
**Vulnerability:** A custom `/storage/{path}` fallback route in `routes/web.php` lacked proper directory traversal guards, enabling unauthorized retrieval of sensitive files like `.env` using path traversal segments (`..` or `\`). Additionally, Laravel 11's default private `local` disk configuration had `'serve' => true` without visibility settings, which silently registered a `storage.local` route on `/storage/{path}` during the framework's `booted` hook, bypassing the custom fallback route entirely and exposing the private file storage under a signature requirement.
**Learning:** Framework-registered routes registered in deferred hooks like `booted()` take precedence over routes loaded earlier in route files. Furthermore, failing to explicitly disable public serving of private file storage disks can result in route hijacking and unintentional exposure of sensitive files.
**Prevention:** Ensure private storage disks have `'serve' => false` in `config/filesystems.php` to prevent the framework from registering public routes on private directories. Secure all fallback file-serving routes with robust path-traversal checks using `str_contains` for relative patterns, and `realpath` matched against a strict prefix boundary to guarantee that files cannot escape their intended storage context.

## 2026-07-31 - Support System IDOR Bypass for Guest Tickets
**Vulnerability:** Guest support tickets (where `user_id` is null) did not have any authorization validation on the message fetching (`getMessages`) and message sending (`sendMessage`) endpoints of the Support System. Since the IDOR guard only checked for authenticated ownership, any request querying a guest ticket UUID could read history and send unauthorized messages on behalf of the guest.
**Learning:** Guest-created records (without associated `user_id` foreign keys) are highly susceptible to IDOR vulnerabilities if fallback authorization logic is not defined. Even when models utilize unguessable UUIDs, failing to restrict non-owner access exposes sensitive conversation logs and messaging actions.
**Prevention:** Secure guest-accessible resources by linking the newly created resource UUID to the guest's session storage on the backend (e.g., in a `guest_support_ticket_uuids` array). Validate the requester against this session container when verifying non-authenticated ownership of the resource.

## 2026-08-01 - Webhook and Redirect Callback Race Condition in Split Payments
**Vulnerability:** When a payment split transaction webhook (`charge.success`) is processed asynchronously before the synchronous user redirect callback completes, the redirect callback would crash with a duplicate entry exception (on guest user email) or attempt duplicate finalize booking operations. This leaves the system in a broken or partially configured state.
**Learning:** Webhooks and frontend redirect callbacks often run concurrently or out-of-order. If guest account creation is not idempotent, or if the redirect handler does not verify whether the booking reference is already processed, race conditions will lead to service failures.
**Prevention:** Always verify if a transaction reference has already been processed (e.g. check for existing booking) at the entry point of both the callback and the webhook. Make user-creation steps idempotent by querying for existence (e.g., matching on email) before performing inserts.

## 2026-08-03 - Media Proxy Path Traversal & Arbitrary File Access
**Vulnerability:** The `/image` media proxy endpoint accepted raw user input for `path` via query parameters and only checked for `str_contains(.., '..')`. This allowed potential directory traversal bypasses on certain setups, and lacked strict boundary enforcement using `realpath()`. Furthermore, it had no MIME-type whitelist, meaning any file type (including code, credentials, or logs) could be disclosed if traversed.
**Learning:** When using custom file serving proxy endpoints, relying on simple string filters is insufficient; canonicalization with `realpath()` must be explicitly verified against the designated root folder boundary. Moreover, enclosing framework-thrown HttpExceptions (e.g. via `abort(403)`) inside overly broad `try/catch` blocks can capture and convert them to `500 Internal Server Errors`, breaking expected HTTP responses in test suites.
**Prevention:** Secure all media serving proxies by canonicalizing paths via `realpath()`, verifying they strictly start with the allowed root directory, and whitelisting served content types (e.g. only matching `image/*` or `video/*`). Structure exception handling blocks carefully to ensure HTTP status exceptions (such as those thrown by `abort()`) are not captured and converted into generic 500 errors.

## 2026-08-04 - Hostel Manager Room Details IDOR Vulnerability
**Vulnerability:** The active room details endpoint `/hostel-manager/rooms/{room:uuid}` mapped to `HostelManagerDashboard::showRoom` lacked any authorization check, allowing any authenticated hostel manager to view arbitrary room details, student occupant profiles, and transaction histories across the entire application.
**Learning:** Duplicate controller implementations (e.g., `HostelManagerController` vs `HostelManagerDashboard`) can lead to situations where security patches are applied to one class while active routes map to another insecure class, leaving critical vulnerabilities unpatched in production.
**Prevention:** Avoid maintaining redundant or duplicate controllers for the same domain. Always check active routing configuration (`routes/*.php`) to confirm the controller and method receiving live traffic. Ensure all model detail endpoints verify resource ownership before rendering sensitive user/occupant data.

## 2026-08-18 - Unauthenticated Authorization Bypass via Null Comparison
**Vulnerability:** `PaymentController::show` checked `if ($payment->user_id !== auth()->id()) { abort(403); }`. For unauthenticated requests (`auth()->id()` is null) querying guest payments (`$payment->user_id` is null), `null !== null` evaluated to `false`, allowing unauthenticated attackers to bypass authorization and view sensitive payment receipts.
**Learning:** Checking ownership using strict equality checks (`$record->user_id !== auth()->id()`) without first verifying that `auth()->id()` is non-null allows unauthenticated requests to bypass authorization when target records have null owner IDs (e.g., guest records).
**Prevention:** Always verify that `auth()->check()` or `auth()->id()` is truthy before evaluating resource ownership, or require authentication middleware explicitly on protected routes.

## 2026-08-06 - Student Complaint Submission IDOR & Hostel Manager Access Control
**Vulnerability:** `StudentController@storeComplaint` accepted a user-supplied `booking_id` without verifying ownership (`$booking->user_id === Auth::id()`), allowing students to link complaints to other users' bookings and hostels. Additionally, `HostelManagerDashboard` methods (`showOccupant`, `exportOccupants`, and `complaints`) queried `Hostel::where('user_id', $user->id)` instead of `$user->managedHostels()`, breaking authorization for assigned managers.
**Learning:** Using generic database lookups on user-provided foreign keys without validating user ownership exposes cross-tenant IDOR vectors. Furthermore, using creator/owner foreign keys (`user_id`) instead of designated operational relationships (`manager_id` / `managedHostels()`) causes broken access control across manager dashboards.
**Prevention:** Always scope user-supplied IDs to the authenticated user (`where('user_id', Auth::id())`) when referencing parent records. Ensure dashboard controllers consistently use role-appropriate relationship methods (e.g. `managedHostels()`) rather than raw entity ownership checks.
